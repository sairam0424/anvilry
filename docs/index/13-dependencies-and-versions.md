# Dependency Inventory & Version Surface

> Part of the Anvilry v3.8.0 codebase index. Master entry point: [docs/index/README.md](./README.md)
>
> **Snapshot:** describes Anvilry v3.8.0 (package `anvilry` 3.8.0), i.e. `main` a929932 (package `anvilry` 3.6.0) plus the five fixes made after it, described by behaviour: notes are hidden at the data layer when `NOTES_ENABLED` is off; rate limiting has per-class buckets (`chat` / `voice` / `beacon`) with a valid-`CRON_SECRET` bypass for the eval cron (`src/lib/cron-auth.ts`); admin auth is centralised in `isAdminAuthorized` (`src/lib/admin-auth.ts`), shared by `src/proxy.ts`, `requireAdmin` and the telemetry page; command-palette talk mode is gated by `isVoiceViewActive`; and `MIN_ROUTES` in `scripts/bundle-budget.mjs` is 17, alongside removal of dead components. The rate-limit, admin-auth, command-palette and bundle-gate fixes show up in the rows below; the notes fix does not touch this surface. Every version, count and `path:line` below was re-read against the `a929932`-plus-fixes tree; `package.json`'s own version, bumped at the release cut, is `3.8.0`.

**Scope:** `package.json` (`dependencies`, `devDependencies`, `engines`), `pnpm-workspace.yaml` (`overrides`, `patchedDependencies`, `onlyBuiltDependencies`, `ignoredBuiltDependencies`, `allowBuilds` — the pnpm settings left `package.json` in v3.5.0), `pnpm-lock.yaml`, `patches/`, `.nvmrc`, and every config / source file that consumes a declared dependency (`next.config.ts`, `vitest.config.ts`, `playwright.config.ts`, `velite.config.ts`, `postcss.config.mjs`, `eslint.config.mjs`, `tsconfig.json`, `vercel.json`, `.github/dependabot.yml`, `.github/workflows/*.yml` — five files: `ci.yml`, `codeql.yml`, `dependency-review.yml`, `gitleaks.yml`, `scorecard.yml` — `Makefile`, and the `src/`, `e2e/`, `scripts/` import sites). Two in-scope files import **no** declared dependency and are indexed anyway: `scripts/bundle-budget.mjs` (`node:fs` only; it enforces the `three` one-chunk / first-load invariant) and `scripts/check-index-citations.mjs` (`node:` builtins only; the gate that keeps this index honest). `scripts/seal-claims.ts` is the one consumer of the `tsx` devDependency. `.github/workflows/bundle-analysis.yml` is **deleted**.

**Files indexed:** 62 (see **Coverage**). The set grew from 47 with the four supply-chain workflows, the `@react-three/fiber` patch, `scripts/seal-claims.ts` and `scripts/check-index-citations.mjs`, the auth / cron / embedding modules, the build-allowlist consistency test, the tooltip wrapper, and the command-palette split.

**Declared counts (measured with node against `package.json`):** `dependencies` = **35** (`package.json:23-59`), `devDependencies` = **18** (`:60-79`), `overrides` = **12** (`pnpm-workspace.yaml:18-43`, the last entry, `qs`, closing the map on `:44`), `patchedDependencies` = **1** (`:49-54`), `onlyBuiltDependencies` = **1**, `allowBuilds` = **3** keys. Total declared = 53. **13** npm scripts (`:8-22`). The pnpm settings are not in `package.json` at all — see **Version pins & overrides**.

**What changed at v3.5.0 (dependency surface only):** `@react-three/rapier` and `@react-three/offscreen` were **removed** (`CHANGELOG.md:372-377`); `flags`, `@upstash/redis` and `web-vitals` (`^5.3.0 → ^6.1.1`) were bumped; the `pnpm` field of `package.json` was deleted and its blocks moved to `pnpm-workspace.yaml`; `engines.node` (`">=22 <23"`) and `.nvmrc` (`22`) were added.

**What changed since v3.5.0 (dependency surface only):** `package.json` gained `@aws-sdk/client-bedrock-runtime` (FAQ-cache embeddings, `src/lib/faq-embeddings.ts`) and `@radix-ui/react-tooltip` (`src/components/ui/tooltip.tsx`) — prod 33 → 35 — and `tsx` (runs `scripts/seal-claims.ts`) — dev 17 → 18 — plus the `seal-claims` script (13 scripts now). Core versions moved to `next` / `eslint-config-next` 16.3.5 / 16.3.4, `react` / `react-dom` 19.3.0, `three` / `@types/three` 0.186.0, `postprocessing` 6.39.5, `@anthropic-ai/sdk` 0.125, `@playwright/test` 1.62.1; `@react-three/postprocessing` went from exact 3.0.4 to exact 3.1.1. `pnpm-workspace.yaml` gained the `@react-three/fiber` patch and two more overrides (`browserslist`, `qs`), and `fast-uri` became an exact pin. `@next/bundle-analyzer` is still declared (`package.json:61`) but is a local, opt-in tool: `next.config.ts:5` wraps the export unconditionally and it only does work under `pnpm analyze` (`package.json:12` = `velite --clean && ANALYZE=true next build --webpack`).

## Version pins & overrides

> **Where pnpm settings live, and how that changed.** `overrides` and `onlyBuiltDependencies` used to sit in `package.json`'s `pnpm` field; that field was deleted in v3.5.0 and `pnpm-workspace.yaml` is now the only place pnpm reads them from (`ignoredBuiltDependencies` already lived there). v3.6.0 added `allowBuilds`, the pnpm 11 successor to the two build-script lists (`CHANGELOG.md:187-204`); after v3.5.0 the file also gained `patchedDependencies` and two more `overrides`. `package.json:3` reads `3.8.0`. The move to a workspace file was security-motivated, not cosmetic — see the `overrides` subsection below.

### `onlyBuiltDependencies` (`pnpm-workspace.yaml:70-71`) — legacy

`["esbuild"]`, tagged in the file `# legacy; honoured only by pnpm <=10.27`. Two `esbuild` versions are in the resolved graph and both are covered because `allowBuilds` keys on the package name: `esbuild@0.25.12` is a **direct dependency of `velite@0.4.0`** (`pnpm-lock.yaml:10048`) and needs its postinstall to fetch/link the platform binary, so content generation would fail without approval; `esbuild@0.28.2` arrives through `tsx@4.23.13` (`:9863`) and now also satisfies `vite@8.0.16`'s optional peer `esbuild: ^0.27.0 || ^0.28.0` (declared `pnpm-lock.yaml:4753`, resolved `:10065`). The `[ERR_PNPM_IGNORED_BUILDS]` failure quoted below was measured at v3.6.0, when `esbuild@0.25.12` was the only esbuild in the graph; `esbuild@0.28.2` arrived later with `tsx` and declares the same `postinstall`, so the name-keyed `allowBuilds.esbuild` entry has to cover both.

### `ignoredBuiltDependencies` (`pnpm-workspace.yaml:74-76`) — legacy

`[sharp, unrs-resolver]` — the inverse list; these two natives are installed *without* running their build scripts. There is now **one** `sharp` in the graph, `0.35.4` (`pnpm-lock.yaml:4364`), reached from `next@16.3.5` (optional dependency, `:9067`) and from `velite@0.4.0` (`:10049`); `unrs-resolver@1.12.2` comes from `eslint-import-resolver-typescript@3.10.1` (`:7619,7628`). This is the one block that always lived in `pnpm-workspace.yaml` — introduced in the repo's initial commit (`git log -S ignoredBuiltDependencies` → `ee0fc1e Initial commit from Create Next App`), which is also why the file already existed for the other settings to move into.

### `allowBuilds` (`pnpm-workspace.yaml:81-84`) — the live setting

`{esbuild: true, sharp: false, unrs-resolver: false}` — a boolean map honoured by pnpm >=10.28 and 11. **The allowlist is deliberately spelled twice** (the file header at `:56-58` says so), but the reason is narrower than "one spelling per pnpm major": the legacy lists are dead config for CI — `pnpm/action-setup` with `version: 10` resolves to the latest 10.x (10.34.5), which honours `allowBuilds` — and survive only for pnpm <=10.27. Measured on a one-install-script fixture with `allowBuilds` alone: pnpm 11.17.0 ok · 10.34.5 ok · 10.28.0 ok · **10.27.1 exit 1** (`pnpm-workspace.yaml:65-69`; `CHANGELOG.md:187-204`). Deleting the lists therefore does *not* break CI; the copy-paste rule that keeps them is "keep them in sync", enforced by `src/lib/pnpm-build-allowlist-consistency.test.ts` (see the guard below).

pnpm 11 removed `onlyBuiltDependencies` / `ignoredBuiltDependencies` outright — it does not consult them for build approval and prints no warning (`pnpm-workspace.yaml:60-64`). Do not cite `pnpm config get onlyBuiltDependencies` as evidence it still honours the key: `pnpm config get` echoes ANY key present in the file, including one that does not exist. When `allowBuilds` is **absent**, pnpm 11 writes it into this tracked file itself, seeded with the literal placeholder `set this to true or false`. That string is neither `true` nor `false`, so every listed package is treated as denied and the install aborts:

```
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@0.25.12, unrs-resolver@1.12.2
```

Measured before the fix (v3.6.0): `pnpm install --frozen-lockfile` **exit 1 on pnpm 11.17.0** from a clean clone (and it dirtied `pnpm-workspace.yaml`), **exit 0 on pnpm 10.34.5**. Because CI pins pnpm 10 the failure was invisible to every green run and reached only contributors on the current default pnpm — *CI passing* and *the repo installing* are different claims. The `install-pnpm-11` job (`ci.yml:204-253`) now covers the gap: frozen-lockfile install on pnpm 11, `git diff --exit-code` so a silent rewrite of a tracked file is itself a failure, then `vitest run src/lib/pnpm-build-allowlist-consistency.test.ts` (`ci.yml:252-253`).

**The guard.** `src/lib/pnpm-build-allowlist-consistency.test.ts` makes two independent assertions: (1) the two spellings agree with each other (catches hand-editing drift), and (2) every dependency in the *resolved* tree that declares an install script appears in `allowBuilds` with an explicit boolean (catches the likelier case — a new dependency arrives and nobody adds it, CI on pnpm 10 warns-and-passes while pnpm 11 exits 1). It runs inside `pnpm build` (via `vitest run`) and in the `install-pnpm-11` job.

### `patchedDependencies` (`pnpm-workspace.yaml:49-54`) — 1 patch

`'@react-three/fiber@9.7.0': patches/@react-three__fiber@9.7.0.patch` — a `pnpm patch` that adds a null-target guard to fiber's `connect()` (pmndrs/react-three-fiber#3754): without it `connect()` called `addEventListener` on a null/undefined target, unlike `disconnect()`'s matching check, crashing the hero graph's WebGL canvas on unmount/remount races. Mirrored in the lockfile at `pnpm-lock.yaml:21-24` (`hash` + `path`) and reflected in every fiber snapshot key as `patch_hash=…`. It is keyed to the **exact** resolved version, while `package.json:33` says `^9.7.0`; the workspace comment says to drop the patch once upstream releases a fix against 9.7.0. Kept separate from `overrides` because a patch edits one resolved version's files rather than choosing which version resolves.

### `overrides` (`pnpm-workspace.yaml:18-43`, last entry on `:44`) — 12 entries

Ten were added in v3.4.2 and relocated in v3.5.0; `browserslist` and `qs` were added later (commit `08913af`, Dependabot #53-#56), and `fast-uri` was since tightened from a caret range to an exact pin. Every override exists to resolve a Dependabot advisory on a **transitive, lockfile-pinned** package. Root cause per commit `2f309d2`: `@modelcontextprotocol/sdk` is pinned exactly to `1.26.0` while 1.30.0 exists, so Dependabot could not walk the chain and reported `security_update_not_possible`; `pnpm update --depth Infinity` also could not move them. All twelve are mirrored into `pnpm-lock.yaml:7-19`.

**Why three of them are exact rather than caret.** pnpm 11's default `minimumReleaseAge` check rejects a lockfile entry that resolves to a version published too recently: `fast-uri` `^3.1.6` re-resolved to 3.1.7 (published <24 h before a run) and broke the `install-pnpm-11` job (`pnpm-workspace.yaml:22-27`); `browserslist` (4.28.8, aged) and `qs` (6.16.0, the only patched release so far, so newer than the usual comfort margin) follow the same reasoning (`:34-38`, `:39-43`). A caret range would just re-resolve to whatever is newest at install time. Bump them deliberately; if pnpm 11's release-age gate rejects `qs`, that is the signal to wait and retry, not to skip the fix.

**Why they moved in v3.5.0, and why it counts as a security fix.** pnpm 11 no longer reads the `pnpm` field of `package.json` — it prints "The \"pnpm\" field in package.json is no longer read by pnpm" and skips it. So on pnpm 11 the ten security-load-bearing pins were being **ignored**. Nothing had broken yet: CI pins pnpm 10 and `pnpm-lock.yaml` already encoded the resolutions, so the resolved graph was correct — but a single `pnpm install` on pnpm 11 would have regenerated the lockfile *without* the `overrides:` block and silently reverted v3.4.2, signalled only by a warning line that reads like boilerplate. Both pnpm 10 and 11 read `pnpm-workspace.yaml`, so it is now the single source of truth that works on either. `CHANGELOG.md:360-364,366-370` records the verification: the lockfile was regenerated with each pnpm major (**byte-identical** both times) and all ten pins confirmed applied in the resolved graph rather than merely declared. The file's own header (`pnpm-workspace.yaml:1-12`) carries the same rationale, and `:15-17` marks the block "SECURITY-LOAD-BEARING. Do not remove one without confirming the advisory is closed by the resolved graph".

## Framework version notes

**Next 16.3.5.** `CLAUDE.md` opens with a standing warning that Next 16 APIs differ from training data and to consult `node_modules/next/dist/docs/`. The decisions below were made in the 16.3.0 upgrade and still stand at 16.3.5. Version-sensitive code found:

- `experimental.viewTransition` was **removed** in the 16.3.0 upgrade (`next.config.ts:134-145`): it no longer exists in Next's `ExperimentalConfig` (absent from `config-schema.js` and the types), so leaving it was a hard typecheck failure.

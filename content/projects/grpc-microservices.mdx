    body: "2PC is the obvious alternative for cross-service atomicity, but it needs distributed locks held across every participant and a coordinator that becomes a single point of failure. Sagas avoid both, but the cost lands on the order flow's consistency model — it's eventually consistent, and correctness now depends on compensating transactions actually reversing partial work cleanly when a step fails midway."
  - title: "At-least-once-with-dedup, not real exactly-once"
    body: "A transactional outbox plus consumer-side dedup plus a DLQ is, underneath, an at-least-once delivery guarantee with deduplication bolted on — not the theoretically pure exactly-once semantics the name gestures at. No write path checks that flag: reservations go to the Postgres writer from any instance, so Postgres row locks, not the election, serialize them. The cost is a coordination dependency with its own failure modes — leader flapping or quorum loss becomes part of this system's failure surface — for a flag nothing enforces, and what happens to in-flight writes during a leader-election gap isn't specified."

A production-style, event-driven order-processing backend built as **polyglot Go + Python/FastAPI microservices** that talk gRPC internally behind a REST gateway, with a **Next.js dashboard** for live orders — a classic backend with no LLM in the loop, and the kind of system distributed-systems interviews probe.

**The hard parts, up front:** Saga-orchestrated transactions (no 2PC) · ACID inventory reservations · a **transactional outbox** · idempotency keys + Dead-Letter Queues · **etcd leader election** · **metric-driven read routing** · Bloom/Cuckoo filters · Redis caching.

- **Saga** distributed transactions + transactional outbox
- **etcd** leader election · replica read routing
- DLQ + idempotency · Bloom filters · Redis cache
- Next.js dashboard · live SSE order updates

> 316 commits on main as of 2026-10-21 and no releases; run it with the Docker Compose stack in `order-processing-system/`.

## Architecture

The system splits into an edge — **Nginx** in front of an **Envoy L7 proxy** that fronts the REST gateway replicas — and internal services that speak gRPC to each other, with Kafka carrying events. The service layer is **polyglot Go + Python/FastAPI**.

- **Nginx → Envoy** — the external entry point; gateway traffic under `/api` goes through Envoy, which balances the two gateway replicas.
- **PostgreSQL** — system of record: a leader plus read replicas.
- **Redis Stack** — cache, Bloom/Cuckoo filters, rate limits, idempotency keys, saga state.
- **etcd** — leader election and the per-node CPU metrics behind read routing.
- **Debezium**, tailing the Postgres write-ahead log (inventory CDC, order outbox).
- **Next.js dashboard** — order flow and cluster views over REST + SSE.
- **OpenTelemetry / Prometheus / Grafana** — tracing, metrics, and dashboards.

## How It Works

1. A request lands at Nginx, then Envoy, then a gateway replica, which checks product ids against a Tier-1 Bloom filter, honours an `Idempotency-Key` through Redis, and calls the order service over gRPC.
2. The order service writes the order and an outbox row in **one local transaction**, then starts a saga; later steps publish to Kafka directly.
3. By default the **Saga** orchestrator service (a Temporal backend exists but is opt-in) keeps its state in Redis and sends Kafka commands: inventory reserves stock in a single **ACID** transaction, then the order completes. A failed completion triggers a stock release and a failed order; a failed release is logged, not retried.
4. A relay in the order service polls the outbox every second (`FOR UPDATE SKIP LOCKED`) and publishes to Kafka; `make cdc-setup` also registers a Debezium outbox connector on the same table, so two publishers exist.
5. The order and inventory services dedupe on recorded event ids. Inventory sends any message it fails to handle to a DLQ topic at once, with no retry in between, and the order streamer dead-letters messages it cannot deserialize. The order service has no DLQ.
6. Inventory nodes elect an etcd leader, but reservations write to Postgres from any instance; the flag is only reported on `/cluster/status`.
7. Stock checks read Redis, then Postgres; reservations pass a Cuckoo-filter and cache check before the locked write. List reads go to a replica picked by hashing the lowest-CPU etcd node — a heuristic, not replica load.
8. The order streamer serves Kafka order events as a gRPC stream, bridged to SSE at `/api/orders/events` for the dashboard.
